0 · 执行摘要

两者不是同一层的产品，这是理解一切差异的前提：

dsh = Harness（引擎）

自己就是 agent 本体。它拥有 agent loop、工具注册表、会话日志、模型适配器、压缩引擎。它要解决的是"如何让一个 agent 跑得又久又准"。

  • ~50 个 packages，Cordis 插件树，"一切皆插件"
  • 自研 LLM 适配、自研 schema DSL、自研 RPC（Typert）
  • 跨平台原生沙箱（bwrap/Landlock/Seatbelt/Win-ACL）
  • 上下文管理是一等公民：独立的 context / compaction / spill / token-meter / session-query 包

Ensemble = Control Plane（控制面）

自己不是 agent，是指挥多个厂商 agent 的工作台。它拥有进程编排、权限 UI、持久化、计费、跨 agent 消息。它要解决的是"如何让多个 agent 协同"。

  • ~21.8k LOC 业务代码（core 10.6k / shared 0.9k / UI 10.3k，不含测试），Tauri + Node sidecar + Next.js
  • Agent loop 委托给 claude CLI / codex CLI / @openai/agents
  • 独有能力：多 pane 布局、peer 消息（continue/review/fork）、Team、跨 runtime 统一渲染、成本核算
  • 上下文管理几乎为零：无预算、无自动压缩、无溢出检测

五句话结论

  1. dsh 的上下文管理是可以直接抄的成熟工程：0.8 触发 / 0.16 保留的比例化压缩、cache-对齐的摘要请求、耐久化的压缩锁、tool-result 先廉价剪枝后昂贵摘要的分层策略、大输出 spill 到磁盘换 handle。
  2. Ensemble 当前最大的风险不是功能缺失，而是"静默撞墙"：OpenAI-compat 路径每轮全量重放 DB 历史且无任何上限，用户只会看到一个泛化的 QUERY_FAILED。
  3. Ensemble 有两个真正领先的点：跨 agent 的有界上下文传递（peer_send 8000 / peer_query 12000 字符硬上限），以及三 runtime 统一的成本/token 核算（dsh 只有 OTel 遥测，没有面向用户的计费视图）。
  4. 结构性困境：Claude/Codex 的上下文在厂商 CLI 的 session 文件里，Ensemble 看不见也管不了 —— 所以 Ensemble 不该去抄 dsh 的 compaction 引擎本体，而该抄可观测性 + 分层裁剪 + spill 这些在控制面这一层就能做的部分。
  5. dsh 明显弱于 Ensemble 的地方：权限模型只有 one-shot ask/never（无"永久允许"）、无 TUI、MCP 只做 client 不做 server、无面向用户的成本视图、概念负担极重。

2 · 架构对比

2.1 dsh：Cordis 插件树

dsh 把 Cordis（一个 DI/插件框架）vendor 进仓库（vendor/cordis, vendor/schemastery, vendor/loader, vendor/hmr…），并 rescope 成 @deepseek-ai/*。vendor/README.md 明说这是为了"完全拥有框架层（可审计、可打补丁、可锁版本）"，并记录了约 18 处对上游的本地修补（fiber 生命周期、Loader 事务化 reconcile、精确路径 HMR）。

docs/architecture.md 的原话："每一个部分都是插件，包括模型适配器、工具注册表、会话日志，以及 agent loop 本身……没有一个特权 core 需要打补丁。"

启动时的插件树 = 分层 patch 叠加：
  profile (web | headless | 自定义)   $DSH_HOME/profiles/<name>
    └─ bundles              packages/bundle/{base,web-app,headless}
       └─ profile 自身 cordis.patch.yml
          └─ home 级 patch
             └─ --patch 覆盖层
  每层按 config row id 定位，可替换或插入
  dsh --profile web --dump-config  ← 打印真实组合结果

Seam 三段式（这是 dsh 最值钱的架构约定）

每个能力拆成 Service Definition（抽象接口 + ctx key）/ Provider（具体实现）/ Consumer（面向模型的工具）。收益是实打实的：packages/e2b 只替换了 ctx.fs 和 ctx.subprocess 两个 provider，Bash、PTY、LSP 三个工具零改动就整体搬到了远程沙箱里。

2.2 Ensemble：三进程 + 一个 seam

Ensemble.exe (Tauri Rust, ~11MB) ── 窗口/托盘/sidecar 生命周期，无业务逻辑
  ├─ WebView2 / WKWebView → http://127.0.0.1:<auto-port>
  └─ ensemble-core(.exe)  (Node 22 SEA, ~100MB)
       ├─ Fastify: 静态前端 + /api/* REST + /ws WebSocket
       ├─ node:sqlite (WAL, 手写 repo shim, 无 ORM)
       │    Provider/Agent/Message/Permission/McpServer/Team/Workspace/AppSetting/UsageEvent
       └─ AgentRuntime seam ── query(opts): AsyncIterable<RuntimeEvent>
            ├─ claude.ts  (~60 行) → @anthropic-ai/claude-agent-sdk → 子进程 claude CLI
            ├─ openai.ts          → @openai/agents 进程内
            └─ codex.ts  (~1000 行) → 子进程 codex exec --json，隔离 CODEX_HOME

端口交接是个不错的工程细节：sidecar 自选空闲端口，用 fs.writeSync(1, "ENSEMBLE_LISTENING <port>") 同步写 stdout（所有日志强制走 stderr 保证 stdout 干净）+ .port 哨兵文件双通道，Rust 侧用 AtomicBool CAS 竞速，12s watchdog 兜底。没有用 Tauri 的 invoke IPC —— 全部走 HTTP/WS，这样 sidecar 能独立 headless 运行。

3 · Agent Loop 归属 —— 一切上下文差异的根源

3.1 dsh 的 loop

在 packages/core/agent-loop（AgentLoop 服务），文档称"整个 harness 里唯一含具体 loop 逻辑的包"。抽象契约在 packages/core/agent（ctx.agents），对 loop 零依赖 —— 所以 UI/hooks/ACP 都面向接口编程，loop 可整体替换。

turn/start → 从 inbox 领取输入 → 装配 prompt+tools → agent/pre-step (可 reject|enter)
  → step/start → agent/request → llm/stream → assistant/chunk* → assistant/message
  → tool/call* → tools/pre-execute → tools/execute → tools/post-execute → tool/result*
  → step/end → (还有未偿还的工作? 回到 step/start) → agent/turn-stopping → turn/end

关键设计：

  • step = 一次模型请求 + 它的工具调用；turn = 零或多个 step。
  • turn/*、step/*、user/message、assistant/*、tool/* 是耐久 session 事件；agent/pre-step、tools/* 是活跃 waterfall（协作式中间件，listener 必须调 next()）。
  • 输入通过一个 inbox、三种投递原语：followup()（下一 turn FIFO + 唤醒）、steer()（下一 step + 唤醒）、inject()（下一 step，不唤醒）。每次 inbox 变更都记日志。
  • 工具并发：按 exclusive / parallel-safe 分类，有界滚动池，maxParallelToolCalls 默认 10。
  • 取消收敛：agent.cancel() 后未派发的 tool call 会补一个合成的 ABORTED_BEFORE_DISPATCH 结果，保证历史一致。
值得单独指出的原则
docs/architecture.md："Model-visible means logged" —— 凡是模型能看到的输入，必须能从 session 日志完整重建。所以 dsh 把运行时上下文（cwd/时间/tmux）做成一条耐久的 user-role 快照消息，而不是塞进 system prompt。这条原则是 dsh 一切上下文可审计性的地基。

OpenAI-compat 与 Codex 路径都是每轮全量重放、无窗口、无裁剪、无摘要。请求体随轮次单调增长，直到上游返回 context-length 错误。而 Claude/Codex 的正常路径又完全不可观测（上下文在 CLI 的文件里）。于是"这个 agent 现在用了多少上下文"没有任何统一答案，只有事后的 token/成本统计。

本次源码复核补充的三条硬证据：

  1. 取历史确实无任何上限。SessionManager.ts:1171 —— prisma.message.findMany({ where:{agentId}, orderBy:{seq:'asc'} })，没有 take、没有 skip、没有任何窗口。而且守卫条件是 isOpenAIKind，其定义（:1165-1168）包含 isCodexKind —— 所以这条无界重放路径不止影响 OpenAI-compat，也影响 Codex，比原文表述的范围更大。
  2. 重放不仅无界，还有损。openai.ts:329-346 buildInputItems 只保留 type==='text' 的内容块，tool_use / tool_result 块被整体丢弃。即：agent 重放历史时看不见自己此前做过哪些工具调用、拿到过什么结果，只剩纯文本对话。这是一个独立于"上下文过大"的正确性问题 —— 长会话中 agent 会重复已做过的操作。
  3. 上下文窗口字段是硬编码的 0，且有注释自认。openai.ts:285 contextWindow: 0, // OpenAI SDK doesn't surface this consistently，codex.ts:722 同样为 0。字段位置已经预留好了，只是从没被填过 —— 这也说明 §11 的 P0 ContextMeter 改动面比预想更小。

4.1 上下文装配：从"拼字符串"到"注册表 + waterfall"

dsh

SystemPrompt（packages/core/system-prompt/src/index.ts，ctx key systemPrompt）按 scope 维护四个独立注册表：

  • sections —— 有序的静态/动态散文块
  • contexts —— 动态运行时快照
  • toolProviders —— schema 贡献者
  • variables —— {{name}} 插值

order 约定形成了一个可预测的分层：

-100   harness:identity          harness 身份
   0   deployment:persona        部署/人格（PERSONA_ORDER）
100-199 工具指导                  e.g. tool-subagent 在 116.5

SystemPrompt.assemble() 跑一个协作式 system-prompt/assemble waterfall，插件可以整体改写 PromptAssembly；然后 renderPrompt() / renderContextSnapshot() 做插值和拼接。工具 schema 顺序由 Config.toolOrder 控制，带一个保留标记 TOOL_ORDER_REST，其余按字典序。

项目记忆是独立包 packages/context/agent-instructions：从 cwd 向上走到 .git 标记的项目根，收集 AGENTS.md/CLAUDE.md 及 *.local.md 覆盖层，加上 harness-home 的全局文件；单文件上限 maxSourceBytes 默认 1,048,576 字节，整批渲染结果受一个必填的 maxBytes 约束；按 trimmed SHA-1 逐目录去重（digest.ts）。

Ensemble

SessionManager.sendMessage 每轮拼：buildEnsemblePrimer()（静态帮助文本）+ plan-mode 通知 + formatActiveSkills()（自动激活的 skill 正文）+ team context 块或 agent 自己的 systemPrompt。然后 sha1 整个装配结果存为 systemPromptHash，一旦哈希变化就强制丢弃 CLI 的 resume 指针 —— 这样改 prompt/team 配置能真正生效，而不被陈旧的 resumed session 掩盖。

Ensemble 这个 hash-invalidation 是好设计
它解决的是一个真实且隐蔽的问题（resume 让 prompt 变更失效）。dsh 因为自己管 session，不存在这个问题。保留它。但它不是上下文管理，只是缓存一致性。
Ensemble 的改进点
当前是命令式字符串拼接，无序、无预算、无去重、无优先级。当 primer + 3 个 skill body（3×4000）+ team block 同时出现时，system prompt 可能已经几千 token，而没有任何地方知道总量。建议引入一个极简版 sections 注册表（见 §11 L1）。

4.2 Token 计量：单一权威 + 双模标注

dsh

packages/llm/token-meter 是唯一测量权威（ctx.tokenMeter）。核心巧思在 TokenMeasurement.baseline.kind：

  • 当"最近一次成功调用的 canonical request envelope"与当前匹配、且其上报总量不低于启发式锚点时 → 'usage'（用真实 provider 数字）
  • 否则 → 'estimated'（用启发式）

启发式（estimate.ts）非常朴素但够用，且递归处理嵌套 tool-result 内容：

CHARS_PER_TOKEN = 4     // 每 4 字符 1 token
BLOCK_OVERHEAD  = 4     // 每个 content block
ROLE_OVERHEAD   = 4     // 每条 message

DeepSeek 适配器（llm-deepseek/src/translate.ts）从 prompt_tokens 中减去 prompt_cache_hit_tokens/cached_tokens，保证 inputTokens 与 cacheReadTokens 互斥不重复计。

溢出不做客户端硬切，而是让它成为 CONTEXT_WINDOW_EXCEEDED_CODE 错误，喂给 compaction 的 overflow 触发器。

Ensemble

local-tokenizer.ts 用 js-tiktoken/lite + cl100k_base/o200k_base 词表（作为 Tauri 外部资源发货，刻意不打进 SEA 以避免杀软误报）。但它的用途是账单审计，不是上下文预算：只统计 OpenAI-compat 轮次（Claude/Codex 子进程的真实 wire bytes 看不到，这两条路径 inputTokensLocal/outputTokensLocal 恒为 0），文档明确承认非 OpenAI tokenizer 有 ±10-30% 漂移，目的是"标记上游明显的超报"。

计费侧倒是相当扎实：每条 result 型消息（三个 runtime 都合成这个形状）转成 UsageEvent 行 —— inputTokens/outputTokens/cacheReadTokens/cacheCreationTokens + 本地计数，成本按 pricing.json + 用户 pricing-overrides.json 计算，打 billingModel: usage|subscription 标（Codex/ChatGPT 订阅轮次边际成本 $0）。粒度：per turn / model / agent（子 agent 向父 rollup）/ provider / day，出现在 UsageStatsDialog 和 /api/usage/summary。与 Message 生命周期解耦 —— 删 agent 不擦成本历史。

最刺眼的一处不对称
Ensemble 唯一的 token 计数机制，恰好只覆盖它三条 runtime 中的少数派。而 Claude/Codex 这两条主力路径的上下文占用，Ensemble 完全无感。dsh 的 baseline.kind 双模思路正好是解药：能拿到 usage 就用 usage（三个 runtime 的 result 消息里都有），拿不到就用 4-字符启发式估，并且把"这是估的"这件事显式标出来。

4.3 压缩（Compaction）—— dsh 最值得抄的一章

三包分工：Service Definition packages/compaction/compaction（ctx.compaction: CompactionEngine）/ 后端 compaction-basic（BasicCompactionEngine）/ 人机入口 command-compact（/compact）。

触发

compactIfNeeded(agent, trigger, signal)，trigger: 'pressure' | 'context-overflow'：

  • pressure：在每一个 agent/pre-step 上检查（serial waterfall，在请求装配之前）。
  • context-overflow：从 agent/request-error 触发，条件是 LLM 错误码为 CONTEXT_WINDOW_EXCEEDED_CODE（packages/llm/llm/src/error.ts）。

阈值（compaction-basic/src/config.ts）

常量默认值含义

范围选择（region.ts: selectCompactableRange）

从尾向头遍历"已计价表面"累加 token，直到覆盖 retainTokens；然后把切点吸附到最近的 toolPairingBalancedBefore/After 成立的边界 —— 即绝不把 assistant 的 tool-call 与它的 tool-result 切开（但允许在一个超大 turn 内部切，"一个超大 turn 的早期已闭合 step 可以独立被压"）。

算法（summarizer.ts: summarizeWithLlm）—— 关键巧思

不是"另起一个摘要请求"，而是：把被压区间自己的 system、tools、派生 messages 原样重放为前缀，然后追加一条合成的 user 消息，内容是固定的 Markdown 清单 COMPACTION_INSTRUCTION：

Primary Request and Intent   主要请求与意图
Key Technical Concepts       关键技术概念
Files and Code               涉及的文件与代码
Errors and Fixes             遇到的错误与修复
Pending Jobs                 未完成的工作
Current Work                 当前正在做的事
Next Step                    下一步
Critical Context             关键上下文

为什么这么做？源码注释说得很直接："逐字重现上一次路由请求的 system prompt、tools 和前导消息……复用 provider 的热前缀缓存。" —— 摘要调用本身就命中 prompt cache，几乎不额外花钱。

产出被 frameSummary 包成 <compacted-summary>…</compacted-summary>，前面加 CHECKPOINT_PREAMBLE，作为一条替换型 user/message 追加，携带 surfaceOp: { op:'replace', start, end }。选定区间之外的一切都不动；区间内除了产出的摘要文本全部丢弃（摘要里出现图片会抛 UNSUPPORTED_CONTENT）。

检查点与锁

compaction/start  ← 这就是锁
  → summarize
  → compaction/summary
  → user/message (replace)
compaction/end

五个事件全是耐久的、只写日志的 SessionEventMap 事件（在 compaction/src/index.ts 用 declare module 声明）。中途崩溃会留下一个有 start 无 end 的孤儿记录，是可检测的。assertNoActiveCompaction 拒绝并发压缩（返回 busy）。针对"压缩期间新 turn 到达"的竞态，有两个不同严格度的稳定性检查：自动路径用 assertWholeSurfaceUnchanged（整表面不变），手动路径用 assertSelectedSpanStable（只要选定区间稳定，容忍区间外的注入）。

防抖

摘要后用 ctx.tokenMeter 重新测量，循环至多 compactionRetries 次，仍超阈值就抛错。溢出重试按 agent 计数并在 agent/status === 'idle' 或一次成功的 assistant/message 后归零。

模型无关的前置廉价通道 ★

Ensemble /compact 的三个具体风险

4.4 Spill：把大输出换成磁盘 handle

packages/spill 不是压缩机制，而是一个 tools/post-execute 策略（spill-policy）。当单个纯文本 tool result 超过 maxInlineBytes（config 门控，不配就整体禁用）时：

  1. 全文通过 ctx.spillStore.saveText()（抽象 seam）持久化到 dsh-spill-local 的私有库：<root>/session-<hash>/<random>-<safeName>
  2. 目录权限 0700，按 sha256(sessionId) 分片；文件用独占 open(path,'wx',0o600) 写入以挫败符号链接竞态
  3. 模型看到的结果被替换为：头/尾预览（TextRetainer，字节预算 50/50 对分）+ 一个不透明的 SpillLocator + 后端提供的 retrievalHint（例如"对该路径用 read 或 grep"）
  4. 通知文本自身的体积算在 cap 之内，所以替换结果永不超过 maxInlineBytes

三个细节体现成熟度：

  • read 调用被豁免模型可见侧的 spill，避免 read→spill→再 read 的死循环；但一个并行的 tools/code-dispatch-log 分支仍然对耐久日志副本同样限界（覆盖 run_code 的嵌套子调用）。
  • 失败即降级：存储出错就保留 inline 结果，绝不把成功变成 isError。
  • fork 出的 session 继承已被引用的 locator，不重复拷贝。
为什么 Ensemble 特别适合抄 spill
Spill 是一个纯粹的"工具结果后处理"，不需要拥有 agent loop 就能做。Ensemble 完全看得见每条 tool_result 事件（它要入库、要广播给 UI）。在入库/转发前挂一个 spill 策略，对三个 runtime 一次性生效，而且顺手解决了另一个现存问题：当前 SDK 消息 payload 是原样入 SQLite 并原样 WS 广播的，一次 cat 大文件就能把 DB 撑肥、把 WebView 卡住。

4.6 Prompt Cache 策略

dsh 在三处显式为 prefix cache 做设计：

  1. Compaction 摘要请求 = 原请求的真前缀（§4.3），所以摘要调用本身命中缓存。
  2. Code Mode 的 SDK 是确定性生成的（packages/code-runtime）：tools.mode: code 时只暴露一个保留的 run_code 传输工具，注册表生成一份确定性的、prefix-cache 友好的 TypeScript/Python SDK，把每个可见工具变成有类型的 async 绑定。只有程序打印/return 的输出会重新进入模型上下文 —— 中间的 tool 返回值永不进入。这同时是 token 成本设计和 cache 设计。
  3. Token 计量区分 cacheRead（§4.2），使 cache 命中在计量上可见。

Ensemble 侧：systemPromptHash 变更即弃 resume 是缓存失效控制（保证正确性），方向与 cache 优化相反但同样必要。真正的 cache 优化（稳定前缀排序、cache breakpoint 放置）由厂商 CLI 内部处理，Ensemble 能做的有限 —— 但它至少可以不要每轮改变 system prompt 的可变部分顺序（当前 skill 自动激活会随消息内容变化而增删 skill body，这会持续打破前缀稳定性）。

一个具体的隐性成本
Ensemble 的 skill 自动激活（scoreSkillMatch，阈值 0.18，最多 3 个，每个正文最多 4000 字符）每轮都可能改变 system prompt 内容。对 Claude 这类靠稳定前缀吃 cache 的 provider，这意味着 skill 命中变化的那一轮会整体 cache miss。改法：把 skill body 从 system prompt 移到第一条 user 消息之后的注入，或者干脆只走 skill_invoke 按需拉取（Ensemble 已经有这条路径了）。

4.9 子代理上下文隔离

dsh 的 ctx.subagents.start()/startContinuable()，按 provider 能力 inheritsParentContext 分两种隔离：

  • 全新子代理：父对话一点不给，必须收到自包含的 prompt
  • fork 子代理：用父的已完成 turn 播种（不含进行中的那个 turn）

无论哪种，tool-subagent/src/index.ts 写着："你收到它的结果，而不是它的中间步骤。"父只拿回 SubagentResult.output —— 于是一个任意深的子代理调查，对父的上下文成本是固定的、很小的一个结果。maxDepth 默认 3 限制递归。可续跑的子代理持久化一个带版本的 subagent/descriptor 事件（SUBAGENT_DESCRIPTOR_VERSION = 2），支持独立于父进程的冷恢复。

Ensemble 的 Task 子 agent 也是 depth ≤ 3、只回传结果，方向一致。subagent-catalog.ts 是一份 8 条的策展目录（Reviewer/Tester/Debugger/Planner/Refactorer/Security-Auditor/Doc-Writer/API-Designer），systemPrompt 模板里带 ${PARENT_CONTEXT_HINT} 占位符；subagent-suggest.ts 用便宜的 prompt（最近 10 条消息、每条头部截 200 字符）让模型挑 3 个目录 key + 短提示（JSON），然后由服务端本地把完整 prompt 灌起来，而不是让模型生成 prompt —— 刻意做便宜（~100 输出 token）且鲁棒（容错的 JSON 花括号提取，模型/解析失败时退回静态默认）。这个设计很务实，是 Ensemble 的一个亮点。

  • OpenAI → NormalizedTool 闭包（sessions/tools/session-aware.ts）
  • Codex → loopback HTTP MCP 桥（mcp-bridge.ts），因为 Codex CLI 无法消费进程内 JS MCP server

三者都按 fromAgentId 闭包绑定，所以自我排除和归属标注行为一致。这个"一套语义、三种传输"的工程量不小，做得也干净。

dsh：三层

  • packages/sandbox（进程约束，ctx.sandbox）：Linux 优先 bwrap，退到 Landlock（自研 native addon @deepseek-ai/node-addon-landlock-run，源码在 native/landlock-run）；macOS 用 Seatbelt（sandbox-exec，allow-default profile 拒 file-write*，白名单 workspace/tmp）；Windows 用 ACL 受限令牌（per-session write SID + 可撤销 ACE）。fail-closed：runner 不可用就返回 SANDBOX_UNAVAILABLE，绝不"降级为不受限"。文档还诚实记录了 Windows 侧的部分强制局限（继承 Everyone-writable 对象、NTFS 硬链接）。
  • packages/interaction：user-approval（ctx.approval，one-shot：allowed-once/rejected/cancelled/unavailable，用 approval/asked+approval/decided 审计，无人应答时 fail-closed）、permission-presets（默认 workspace-write = workspace-write 沙箱 + ask；danger-full-access = 全权 + never-ask）。
  • packages/guard：repeat-tool-reminder（重复调用的忠告式提醒）、timeout-policy（按调用武装 deadline）。
dsh 的明确短板（它自己列在 Known Limitations 里）
ApprovalPolicy 只有 ask 和 never —— 没有 per-tool 白名单、没有"记住这个规则"、没有撤销。ask 模式下每次都要重新问，never 模式下整个 session 放开。原文："Only one-shot grants exist."这在实际使用中相当难受，Ensemble 的 per-turn autoAllowedTools 缓存反而更实用。

Ensemble

刻意二态（CLAUDE.md §准则2："不是规则引擎"），但按 runtime 差异化落地（§3.7 表）：Claude 走 canUseTool → WS permission_request/permission_response 往返 + per-turn autoAllowedTools 缓存（点一次 Allow，本轮该工具不再问 —— 这正是 dsh 缺的）；OpenAI 走 Agents SDK 的 needsApproval 中断-恢复循环；Codex 完全没有 per-call 门，唯一边界是 sandboxMode（read-only/workspace-write/danger-full-access）烧进隔离 CODEX_HOME/config.toml，并显式设 approval_policy = "never"（非交互 CLI 无法被询问）。

7 · 多 Agent 编排

dsh：垂直的委托栈

包能力
subagent委托 seam，可同时注册多个具名 provider：spawn-in-process（全新）/ fork-in-process（从父已完成历史 fork）/ acp（跨进程 ACP）/ codex（真 Codex app-server 子进程）/ claude-code（官方 Claude Agent SDK 子进程）/ dsh-sdk（跨进程 dsh 子进程）
workflow模型编写的编排脚本，跑在 worker thread（明确说明不是安全边界）；tool-ralph 是固定的 fresh-agent Ralph 模式
jobs通用后台任务注册表（owner 隔离的 observe/cancel/wait/complete）—— 长时工具调用、subagent 都挂在这个底座上
schedulesession 局部定时跟进，无外部通知通道（见 §4.7）
goal/plan/todosession 范围的目标/计划/清单状态
值得注意
dsh 的 subagent 不局限于"再起一个自己" —— 它可以是完全不同厂商的 agent 产品（Claude Code、Codex）。这是很有远见的抽象。

Ensemble：水平的协同面

  • 两套正交结构：Agent.parentId 树（Task 子 agent，depth ≤ 3）+ Team 分组（W21）。
  • Team context 注入：buildTeamContext 生成一个重度工程化的 "TEAM CONTEXT" system-prompt 块 —— 逐字角色 + 团队使命 + 队友名册 + 一份命令式清单，强迫模型真的去调 peer_send 而不是输出无效的 @提及（作者们与这个失败模式反复搏斗过，代码注释有记录）。
  • Peer 模式：continue（交接进行中的工作）/ review（二次意见审计）/ fork（刻意走不同路径，明确警告不要复现来源路径）/ raw（纯转发）。都是模板化的指令注入 + 有界 source-output 嵌入。
  • UI 面：AgentTree 侧栏 + 二叉树 LayoutRenderer（pane 分割），布局持久化在 Workspace 表（shared/src/layout.ts，CLAUDE.md 要求 100% 单测覆盖）。
Ensemble 多 agent 的结构性弱点
跨 agent 协同的正确性目前依赖 prompt 遵从，而不是协议保证。那份"强迫调 peer_send"的巨型命令式清单本身就是症状 —— 模型可以无视它。dsh 在这点上是靠 ctx.jobs + subagent 的结构化返回值保证的：父不是"希望"子回报，而是 await 一个 SubagentResult。

可借鉴：为 peer_send 增加一个可选的同步/等待模式（返回接收方的结论，而不只是 "delivered"），让编排从"喊话"变成"调用"。

10 · 优缺点总账

dsh 优势

  • Seam 纪律真的兑现了：E2B POC 只换两个 provider 就让 bash/PTY/LSP 整体搬迁，这是架构红利不是营销
  • 上下文工程是一等公民：独立包、明确阈值、耐久锁、分层降本
  • Code Mode 是有原创性且想得很透的设计（token 成本 + prefix cache 双收益）
  • 多 agent 后端的开放性：subagent 可以是 Claude Code / Codex，而不只是自己的克隆
  • 跨平台原生沙箱，且诚实记录局限而非过度宣称
  • 100% per-file 覆盖门禁、强制 snapshot 回放、数十个 verify 脚本 —— 对 "developer preview" 而言纪律惊人
  • 中英双语文档 + Agent Notes 决策档案
  • Hook 协议兼容 Claude Code / Codex 现有 hooks.json

dsh 劣势

  • 批准模型不成熟：只有 one-shot ask/never，无"永久允许"/无规则/无撤销（自己列为已知局限）
  • 无一等公民 TUI；CLI README 里的 --profile tui 只是假设性例子
  • MCP 只做 client，不能把自己暴露成 MCP server
  • E2B 自标 POC；workflow 的 worker-thread 隔离明确不是安全边界
  • loop 本身没有 turn 预算 / 跑飞上限，要靠 agent/turn-stopping 自行组合
  • 全线 developer preview，明示不保证兼容（SQLite schema、session 格式无承诺）
  • OAuth 类 provider（需存储/刷新 token）在通用 pi-ai 适配器里不支持 —— "带上你的 Anthropic/OpenAI 订阅登录"这条路没有
  • 概念负担极重：插件-事件-seam-disposer 处处皆是，上手成本高
  • 无面向用户的成本/用量视图（只有 OTel）

Ensemble 优势

  • 定位清晰且不重复造轮子：不重实现 agent loop = 不继承 loop 的正确性风险
  • 三 runtime 统一体验：所有消息都规整成 Claude SDK 形状，前端零 runtime 分支
  • 成本可见性优于 dsh：UsageEvent + pricing.json + 用户覆盖 + billingModel: usage|subscription 区分订阅 vs 计量，多维度聚合，与 Message 生命周期解耦
  • 跨 agent 有界上下文传递：peer_send/peer_query/conversation_search 三件套，每条通道都有硬 cap
  • 批准 UX 优于 dsh：per-tool + per-turn 缓存 + 原生弹窗
  • Skills 渐进披露基本追平 dsh：4 来源合并、目录常驻、正文惰性
  • systemPromptHash 失效 resume —— 解决了一个隐蔽的真实 bug
  • subagent-suggest 的"模型只挑 key、服务端灌 prompt"很务实
  • 桌面原生分发（SEA + NSIS/MSI/DMG），端口交接、stdout/stderr 分离等细节工程扎实

Ensemble 劣势

  • 零上下文窗口意识：无预算检查、无自动压缩、无溢出预警。用户不知道要敲 /compact 就会撞墙，只看到泛化 QUERY_FAILED
  • OpenAI-compat 每轮全量重放 DB 历史且无上限 —— 结构性的成本与失败双风险
  • 上下文处理跨 runtime 不一致：Claude/Codex 在 CLI 文件里（不可见），OpenAI 在 DB（无界）；没有统一的"这个 agent 现在用了多少"
  • /compact 粗糙：单次 quickQuery、45s 硬 abort、无重试、无质量校验、不留尾部、DELETE 后无 undo
  • 本地 tokenizer 只覆盖少数派 runtime，且自认 ±10-30% 误差
  • tool result 零裁剪：原样入 SQLite + 原样 WS 广播，大输出能撑肥 DB、卡住 WebView
  • 无 CI、前端零测试、双平台发布靠人肉
  • 加功能要三处同改（三个 runtime adapter），CLAUDE.md 靠纪律约束而非类型强制
  • 跨 agent 协同靠 prompt 遵从而非协议保证（那份巨型命令式清单就是症状）
  • Codex 的 HTTP MCP 桥是"委托厂商 CLI"架构的结构性代价（本地回环 + bearer token 已算合理，但仍是攻击面）
  • Skill 自动激活每轮改变 system prompt，持续破坏 prefix cache
  • 无 hooks 体系；MCP 只能全局不能 per-agent

11 · Ensemble 该学什么（可落地清单）

排序原则：在"控制面"这一层就能做到的优先；需要拥有 agent loop 才能做的，降级或改造。

P0 上下文可观测性 —— 从"完全无感"到"有仪表盘"

借鉴：dsh token-meter 的 baseline.kind: 'usage' | 'estimated' 双模思路。

  • 建一个 ContextMeter，为每个 agent维护一个"当前上下文估算占用"。数据来源分优先级：
    1. 该 agent 最近一条 result 消息里的上游 inputTokens + cacheReadTokens + cacheCreationTokens（三个 runtime 都合成 result 形状，所以这条对 Claude/Codex 也有效）—— 标 usage；
    2. 拿不到就用 dsh 的启发式（CHARS_PER_TOKEN=4、BLOCK_OVERHEAD=4、ROLE_OVERHEAD=4，递归进 tool_result）对 Message 表估 —— 标 estimated。
  • 把 model → contextWindow 的映射补进 pricing.json 旁边（当前 contextWindow 字段是合成的、恒为 0）。
  • UI：每个 pane 标题栏一个细进度条 —— <60% 灰、60-80% 黄、>80% 红，hover 显示 "≈128k / 200k（估算）"。
为什么这是 P0
这一改把 Ensemble 最大的缺陷（静默撞墙）变成可预见的事件，而且不需要拥有 agent loop —— 纯粹是对已有 UsageEvent 数据的再利用。改动面小，用户价值极高。

P0 溢出错误的专门处理路径

借鉴：dsh 的 CONTEXT_WINDOW_EXCEEDED_CODE → agent/request-error → overflow 触发 compaction。

  • Ensemble 已有一条"陈旧 resume"的自愈路径（CLI 报 "No conversation found with session ID" → 清 lastSessionId 并提示重发）。照同样的模式加第二条：识别各 runtime 的 context-length 错误特征（Anthropic 的 context_length_exceeded、OpenAI 的同名 code、Codex 的 stderr 模式）。
  • 命中时不要报泛化 QUERY_FAILED，而是发一个明确的 CONTEXT_OVERFLOW 状态 + 一个"立即压缩并重试"的按钮（甚至可配置为自动执行）。
  • 为 overflow 自动压缩加上 dsh 的防抖：per-agent 重试计数（maxOverflowRetries = 1），在 agent 回到 idle 或成功产出一条 assistant 消息后归零。

P0 Tool result 裁剪 + Spill

借鉴：dsh packages/util/output-retention + packages/spill。这是最适合 Ensemble 抄的一块 —— 纯粹的工具结果后处理，不需要 agent loop。

  • 在 SDK 消息入 Message 表 / WS 广播之前挂一个策略：单条 tool_result 文本超过 maxInlineBytes（建议 32KB 起）时落盘到 DATA_DIR/spill/session-<sha256(agentId)>/，模型/UI 看到的是头尾各半的预览 + 文件路径 + 检索提示（"用 Read/Grep 读该路径获取全文"）。
  • 照抄 dsh 的三个安全细节：目录 0700、文件 open(path,'wx',0o600) 独占创建、存储失败就保留 inline 而不是把成功变成错误。
  • 照抄"通知文本自身算在 cap 内"，保证替换后一定不超预算。
  • 照抄 read 豁免（避免 read→spill→再 read 死循环）。
  • 裁剪库本身做成共享 util（head/tail/headTail，UTF-8 边界安全），中立的 "已省略 N 字节" 文案由调用方补充恢复措辞。
顺带收益
这一改同时解决三件事：模型上下文膨胀、SQLite 膨胀、WebView 卡顿。对三个 runtime 一次性生效，因为它作用在统一的 RuntimeEvent 出口。

P0 修复重放丢弃工具调用（本次复核新增）

这一项与上下文管理正交，是独立的正确性缺陷，但因为同在重放路径上，适合与 P0 一并处理。

  • 现状：openai.ts:329-346 的 buildInputItems 只保留 type === 'text' 的内容块，tool_use / tool_result 被整体丢弃。且上游取历史时（SessionManager.ts:1174-1175）已先按 type === 'user' || 'assistant' 过滤，工具调用信息在两道关卡都被削掉。
  • 后果：OpenAI-compat 与 Codex fallback 路径的 agent，重放历史时看不见自己此前调用过哪些工具、拿到过什么结果。长会话中会重复执行已完成的操作（重复读同一文件、重复跑同一条命令），也会在被追问时声称"我没有做过"。
  • 改法：把 tool_use/tool_result 块映射成 @openai/agents 对应的 input item 类型（function call + function call output 配对），并保持配对完整性 —— 这正好与 P0 的 spill/裁剪 协同：spill 之后 tool_result 已经是有界的预览文本，重放它们的成本可控。若暂时不映射，至少应降级为一行文本摘要（如 [已调用 Read(src/a.ts)，返回 1.2KB]）而不是完全静默丢弃。
  • 验收：长会话中让 agent 回答"你刚才读过哪些文件"，应能正确列出而非否认。

P1 重做 /compact：留尾 + 结构化 + 原子

借鉴：dsh compaction-basic 的三个核心决策。

抄什么具体做法
比例化留尾不再全删。按 retainRatio = 0.16 从尾部保留最近消息，切点吸附到 tool_use / tool_result 配对边界（绝不切开一对）。这直接治好"压缩后 agent 忘了自己刚在改哪个文件"。
结构化摘要清单把 "5-12 句" 换成 dsh 的 8 段清单：主要请求与意图 / 关键技术概念 / 涉及文件与代码 / 错误与修复 / 未完成工作 / 当前工作 / 下一步 / 关键上下文。这是零成本改动，纯 prompt 替换，收益立竿见影。
原子性不再直接 DELETE。写一条 compact_start 标记行 → 生成摘要 → 插入摘要行 → 写 compact_end → 把旧消息标记为 archived 而不是删除（新增 Message.archived 列，查询默认过滤）。这样既有 dsh 的崩溃可检测性（孤儿 start），又免费得到 undo 能力。
前置廉价剪枝在调用摘要模型之前，先对表面上已有的超大 tool_result 做确定性头/尾剪枝并重新估算 —— 如果这一步就降到阈值以下，整个摘要调用省掉。（如果 P0 的 spill 已上线，这一步大部分已被前置解决。）
可配置MAX_TRANSCRIPT_CHARS = 60000 这类硬编码改成 per-provider/model 可覆盖，参考 dsh 的 modelPolicies[]（并校验 retain < threshold）。
但要诚实标注一件事
对 Claude/Codex 路径，Ensemble 的 /compact 本质是"带摘要的重启"（清 lastSessionId，让 CLI 开新 session），不是真正的原地压缩 —— 因为上下文不在 Ensemble 手里。UI 上应该把这件事说清楚（例如按钮文案 "压缩并重启会话"），否则用户会误以为语义与 claude 内建的 /compact 相同。

P1 自动压缩（阈值触发）

  • P0 的 ContextMeter 上线后，在 sendMessage 派发之前检查一次（对应 dsh 的 agent/pre-step pressure 检查点）。
  • 阈值直接用 dsh 的默认值起步：thresholdRatio = 0.8、retainRatio = 0.16。
  • 但默认设为"提示"而非"自动执行"：Ensemble 是有人在看着的桌面工具，且它的压缩会重启 CLI session（副作用比 dsh 大）。给一个 per-agent 的 autoCompact: off | prompt | on 设置，默认 prompt。

P1 把 conversation_search 提升为"agent 自查记忆"

借鉴：dsh session-query + tool-session-query —— 可检索的历史是比压缩更优的方案（压缩有损，检索无损且按需）。

  • 基础设施 Ensemble 已经有了（conversation_search，默认 scope=team，支持 scope='self'）。缺的是定位和引导。
  • 在 buildEnsemblePrimer() 里明确告诉模型："你不需要在上下文里保留旧的细节。用 conversation_search(scope='self') 检索你自己的历史。"
  • 压缩摘要里主动写入一行指针，例如 "更早的细节可用 conversation_search 检索（覆盖 seq 1-847）" —— 这让有损压缩变成"有损 + 可回溯"。
  • 加一个 readMessage(seq) 之类的有界精读工具（对应 dsh 的 readEvent/traceEvent）。
最高投入产出比的一项
几乎不用写新代码，主要是 prompt 引导 + 一个小工具。但它把 Ensemble 的 Message 表从"UI 的显示数据"升级成"agent 的外部记忆"，这是定位上的质变，也正好利用了 Ensemble 相对厂商 CLI 的独特优势 —— 它有一个统一的、跨 runtime 的、可 SQL 查询的完整 transcript，而厂商 CLI 各自的 session 文件没有这个。

P1 修掉 skill 自动激活对 prompt cache 的破坏

  • 现状：scoreSkillMatch 每轮按消息内容决定注入哪些 skill 正文（≤3 个 × ≤4000 字符）到 system prompt，命中变化即整体 cache miss。
  • 改法（择一）：(a) 把 skill 正文移出 system prompt，作为首条 user 消息后的注入内容；(b) 只保留 skill_list/skill_invoke 按需路径（Ensemble 已有），把自动激活降级为"在消息里附一行提示：检测到相关 skill X，可用 skill_invoke 加载"。
  • (b) 更符合 dsh 的渐进披露哲学，且顺带省下每轮最多 12000 字符的固定开销。

P2 peer_send 增加同步模式

借鉴：dsh subagent 的结构化返回值（父 await 一个 SubagentResult，而不是"喊话"）。

  • 给 peer_send 加可选的 wait: true：阻塞到接收方产出结论，返回其结论文本（复用现有的 8000 字符 cap）。
  • 这让 review 模式从"希望对方会回复"变成"拿到审计结果"，把跨 agent 协同的正确性从prompt 遵从推向协议保证 —— 直接缓解 §7 指出的结构性弱点，也能让那份巨型命令式 TEAM CONTEXT 清单瘦身。

P2 状态外置：todo / goal

  • 加一个 Ensemble 级的 todo_write MCP 工具（对应 dsh packages/todo：一个 session 一份清单，刻意不做 provider 抽象）。清单存 DB、显示在 pane 侧边，不占 transcript。
  • 对 Ensemble 尤其有价值：多 agent 场景下，一份共享的、team 可见的 todo 清单同时是编排状态和上下文减压手段 —— 这是 dsh（单 agent 视角）想不到的组合。
  • 参考 dsh packages/schedule 的克制：不做外部通知通道，耐久状态就在日志/DB 里，等 agent 活跃时通过普通 followup 送回。

P2 Hooks 桥

  • dsh 的 hooks-claude-code/hooks-codex 把两家的外部 shell hook JSON 协议翻译到统一面上。Ensemble 做这件事的成本比 dsh 低得多 —— 它本来就在 spawn 这两个 CLI，处在能拦截/注入 hook 配置的位置（Codex 已有隔离 CODEX_HOME + 合成 config.toml 的先例）。
  • 价值：用户现有的 hooks.json 在 Ensemble 里直接生效，是很实的迁移友好性卖点。

P2 工程门禁（与上下文无关但风险最实）

  • 一个 GitHub Actions：tsc --noEmit + 现有 22 个测试 + 前端 build。挡住绝大多数回归。
  • desktop-ui 至少给 store / hooks 加测试（当前 0 个）。
  • 参考 dsh 的 test:snapshot：录一组无密钥的 WS 事件流回放（create→message→permission→result），作为跨 runtime 行为的回归网 —— 这对"三个 adapter 必须行为一致"的硬约束是最合适的验证手段。

P2 · Code Mode（长期观察项）

dsh 的 Code Mode 是本次对比里对上下文影响最大的单项设计（中间 tool 返回值永不进入上下文）。但 Ensemble 不拥有工具注册表，无法直接实现 —— 工具来自厂商 CLI。可行的近似：Ensemble 可以提供一个 run_script MCP 工具，让 agent 写脚本调用 Ensemble 自己的横向能力（peer/search/skill/todo）并只返回最终输出。价值有限但方向正确，且随着 Ensemble 自有工具增多而增值。

12 · 不该学什么（保持定位）

dsh 的做法Ensemble 不该学的理由
Cordis 全插件化 + vendor 框架Ensemble ~24k LOC、单人维护。dsh 的插件树是为"~50 包 + 多前端 + 第三方生态"付的税。Ensemble 该做的是把 AgentRuntime 这一个 seam 做扎实（例如用类型强制新能力必须实现三个 adapter，替代 CLAUDE.md 的纪律约束），而不是引入插件框架。
自研 schema DSL / 自研 RPC (Typert)纯粹的规模驱动决策。Ensemble 用现成方案是对的。
自己实现 agent loop这是 Ensemble 最重要的战略选择，CLAUDE.md §2.1 明确禁止（"永不用 claude -p 替代 SDK"）。不重实现 = 不继承 loop 的正确性风险，自动跟随厂商升级。坚持。
原生沙箱（bwrap/Landlock/Seatbelt/Win-ACL）工作量巨大且平台特异。Ensemble 该继续借用 Codex 自带沙箱，并推动厂商 CLI 补齐 —— 而不是自己写 native addon。
one-shot 批准模型这是 dsh 的短板，Ensemble 现有的 per-turn autoAllowedTools 缓存已经更好用。别倒退。
tool-cordis 自我修改让模型定义并运行动态插件（node:vm）对研究 harness 很酷，对一个分发给用户的桌面产品是安全负债。
100% per-file 覆盖门禁对单人项目会直接压垮迭代速度。Ensemble 现有的分级策略（layout 引擎 100%、其余合理覆盖）是对的 —— 只是需要一个 CI 去执行它。
"developer preview，不保证兼容"Ensemble 已经在分发安装包给真实用户，DB schema 的 ALTER TABLE ADD COLUMN 幂等演进策略是合适的选择。别学 dsh 的破坏性态度。
